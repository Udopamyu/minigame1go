# ミニゲーム1GO｜ゲーム制作・改修プロトコル

**版:** v1.0 ／ **策定日:** 2026-11-18 ／ **状態:** レビュー用・提案仕様（本書の新規項目は、本人が個別に合意するまでは新しい強制ルールとみなさない）

**目的:** 今後のゲーム制作について、①ユーザーは何を指示すればよいか、②AIはどう設計・実装・検証すべきか、③修正をどう収束させるかを定義する。過去作品の良さを失わず、PATROLで効果があった「具体的な完成像と実画像に基づく反復」を再現する。

**適用:** ミニゲーム1GOの新作、独立試作、既存作品の改修。ただし公開済み・開発終了作品は、明示的に再開を指示されるまで変更しない。

**この文書の位置づけ:** 過去の本人指示と現行GitHub資料の要点を整理した部分と、PATROLの経験から追加する**AI運用の推奨手順**を分けている。桜井スキルは**外部参考資料**であり、本人の指示や既存ルールと同一視しない。

## 0. 最初に読む1ページ：使い方

ユーザーは毎回、長大な仕様書を書く必要はない。「何が面白いか／どんな絵か／どう操作したいか／何を守るか」を伝えればよい。残りの技術設計とQA計画はAI側が補う。

| 指示の項目 | ユーザーが指定すると効果の大きい内容 | 未指定ならAIがやること |
| --- | --- | --- |
| CONCEPT（核） | 何を操作して、どの瞬間が楽しいか | 核のループと、類似作品との差を短く定義する |
| LOOK（絵） | 画風、色、世界、キャラ形状、参考画像・作品 | カラーパレットとシルエットの方向性を一案にまとめる |
| FEEL（手触り） | 速い／重い、入力の反応、カメラ、エフェクト | 具体的な調整パラメータと比較可能な試作を作る |
| SYSTEM（ルール） | 勝敗、報酬、リトライ、成長、進行 | 必要最小限のゲームループを設計する |
| KEEP / CHANGE | 絶対に残すもの、変えてよい範囲、開発終了作品か | 既存版のコード・UI・仕様を確認し、回帰防止項目を立てる |
| QUALITY BAR（合格） | どの画面・操作・端末を実画像・実操作で確認すべきか | 自動QA＋スクリーンショット＋短い人間評価の観点を用意する |

**最短の依頼例（新作）**

> 粒子の塊を砕いて吸収する高速アクションを1本。暗い幻想世界、明確なシルエット、破壊時に大量の色粒子。主操作は移動＋突進。スマホ対応でプレイ画面の文字はなし。PCとスマホの実画面を撮影し、見た目と操作感を直してから渡して。

**最短の依頼例（改修）**

> 公開版のUI・装備・進行はそのまま。今回は移動の疾走感だけ改善。押した瞬間に動き、ダッシュに残像を出す。修正前後の画像と操作テストを見せて。既存の公開版は変更しない。

**PATROL型の詳細依頼が効く場合:** 「独創的な世界観・機体デザイン・飛行体験」を狙うときは、季節・時間・光と影・色・シルエット・カメラ・入力・使う技術・完成前に撮るべき画面まで指定する。詳細さそれ自体ではなく、**完成イメージと合否判定の精度**が重要。

## 1. 情報の優先順位と混同禁止

| 区分 | 意味 | 扱い |
| --- | --- | --- |
| **U：本人指示** | ユーザーが明示して採用した条件 | 同じ対象・項目では最新の本人指示が最優先 |
| **I：実装確認** | ソース、実画面、実テストで確認した現在値 | 現状の証拠。本人がその数値を要求した証拠ではない |
| **D：既定方針** | 複数作から抽出した共通の出発点 | 作品固有の明示条件があれば変更可能 |
| **P：AI提案** | 今回の仕様整理や試作における提案・仮説 | 採用済みと書かず、必要なら提案として提示 |
| **R：外部資料** | 非公式「桜井スキル」などの第三者の知見 | 出典を付け、適合性を吟味。自動的に本人指示へ格上げしない |

- 作品の区分（本線／試作／別派生／公開済み／開発終了）を最初に特定する。新しい表現を学んだからという理由で全作品を変更しない。
- **通常のプレイ画面に文字を置かない**のは現行の本人指示（U）。タイトル画面、必要時に開く説明・装備・設定画面は別に設計し、色・形・動き・ゲージで伝える。ただしPATROLのように**その作品について明示された計器や文字情報**があれば、個別指示を優先する。
- **直前にユーザーが褒めた部分、変更を依頼されていない部分は保護する。** 既存のUI・デザイン・ルート・保存・速度を「ついで」に改造しない。
- 「投石機研究所」は本人指示により開発終了。「ロボサルベージのTPS化」も後の本人指示で中止。再開依頼なしに修正しない。2D版との混同も禁止。
- 新作へロボ固有の4部位／全ロスト／10マス分岐、投石機の10面、ブランコの10回・8強化などを一律移植しない。

## 2. ユーザーからの依頼：必要な情報と裁量

### 2.1 アイデア段階（短い指示でよい）

ユーザーは「テーマ、面白さの核、気になる表現」を示す。AIは一画面で伝わる複数案を比較し、**それぞれの1分間のプレイ体験、主操作、リスクと報酬、差別化点**を提案する。選ばれた案は試作へ進める。自由度の高い段階で過剰な質問票を出さない。

### 2.2 新作の実装依頼（可能なら指定）

1. **遊びの核:** 「何をすると気持ちいいか」を動詞で。例：砕く、跳ね返す、滑る、巻き戻す。
2. **LOOK:** 画風、時間帯、主役と背景の形、3〜5色の雰囲気、印象的な光や素材。例：「秋の湖、金色の霞、紫の影」。
3. **FEEL:** 軽快／重量感、入力への反応、速度、カメラ、短い気持ちいい演出。例：「旋回は鋭く、ブレーキでドリフトする」。
4. **操作:** PCとスマホの主操作、同時押し、片手／両手、ボタンの数。未指定ならAIが最小化。
5. **ルール:** 1周の時間、勝敗、報酬、再挑戦、難易度。指定がなければ核を邪魔しない最小構成。
6. **技術制約:** 単体HTML、ライブラリなし、Canvas／WebGL、オフライン、保存、端末など必要な場合のみ。
7. **成功条件:** 具体的にスクショを撮る場面、実操作で到達させる状態、耐久時間、残してはいけないバグ。

**役割分担:** ユーザーは「何を楽しませたいか」と「外せない美意識」を決める。AIは「どう実装するか」「数値の初期値」「QA方法」「失敗時の代案」を自力で設計する。すでに決まった条件を何度も聞き直さない。

### 2.3 改修依頼（最も重要な3点）

- **変えるもの:** 現象と理想（例：横移動がもっさり → 初動を鋭く、疾走エフェクト）。
- **残すもの:** UI、ゲーム進行、保存データ、色、既存装備などの不変条件。
- **確認方法:** 特定の画面、操作、再現動画、旧版との比較。スクショ1枚だけでも有効。

ユーザーが「なんか違う」「ダサい」「楽しくない」と言った場合、AIは主観を否定しない。**シルエット／配色／カメラ／操作反応／密度／情報量／ルール**へ仮説分解し、最も影響の大きい1〜3要因を特定して修正する。実装を丸ごと作り直す前に、既存の良い部分を列挙する。

## 3. AIの作り方：実装に入る前の契約

### Gate 0｜既存資産と完成像の確認

- リポジトリの `AGENTS.md`、共通指示書、作品仕様、決定履歴、現行ソース・PRを確認する。外部参考は独立して読む。
- 既存改修ではUI・入力・プレイ速度・進行・保存・配色を**変更前のスクリーンショットまたは計測値**で基準化する。変更範囲を明文化する。
- 新作では**見た目の主役・最初の30秒の遊び・主要入力・確認したい瞬間**を最低限固める。重要な未指定事項は合理的な仮定で試作し、採用済みと偽らない。

### Gate 1｜小さくても完成形の「縦切り」を作る

- まず**操作 → 反応 → 成功／失敗 → 再試行**が1周できる状態を作る。難しい技術（点群、積層スプライト、地形シェーダー等）が核なら**見た目の技術検証画面**も先に作る。
- いきなりショップ、数十ステージ、アイテム100種を詰め込まない。小さな完成品質を確保してから拡張する。
- アート・UI・操作・効果音を後回しの「仮置き」にしない。最初の遊べる版でも表現の方向性を揃える。
- ユーザーが「単体HTML・ライブラリなし」と指定した場合、配布物は本当に単体で動作すること。許可された外部依存以外は追加しない。

### Gate 2｜LOOK：絵の一貫性を作る

- **色彩設計:** 時間帯、光源、影の色、背景と主役の明度差、限定パレットを定義する。
- **シルエット:** 形で機種、敵、装備、危険物を見分けられるようにする。色違いだけで識別させない。
- **情報の優先順位:** 主役・敵・当たり判定のある地形＞装飾。背景が派手でも遊びを邪魔しない。
- **見た目と物理の一致:** 高低差・障害物・射線・当たり判定・着弾地点の矛盾を検出する。
- **ドット絵／低解像度:** 単なるぼかしや粗いレンダリングで代用せず、ドット単位の形と輪郭を確認する。最近傍拡大、パレット、ディザは作品ごとの狙いに応じて採用する。
- 参考画像がある場合、真似る対象を**形・色・構図・リズム**として明記する。特定の作家・製品の画面を無断で丸ごと複製しない。

### Gate 3｜FEEL：自分で操作している感覚を作る

- 入力してから動き出すまでの遅延、初動加速、停止、逆入力、急旋回、ダッシュ、着地、衝突を実操作で調べる。
- **最高速だけでなく、入力と映像の因果が重要。** ユーザーが期待した瞬間に反応し、画面の追従やエフェクトが速度を補強すること。
- 同一挙動に対して、残像・軌跡・風切り・画面振動・ヒットストップ・短い効果音を適切に使う。盛りすぎて視界やコントロールを失わせない。
- カメラは主役や標的、飛翔物を見失わせない。独自のカメラ切替を作るときは「視点が実際に動いているか」を確認し、単なる画面の切替で代用しない。
- PC・スマホの**同時入力**、指の届きやすさ、誤発動、画面を隠すUIを評価する。

### Gate 4｜SYSTEM：要素に意味を持たせる

- ボタン、武器、強化、敵の行動、ステージギミックには**使い分ける理由**があること。
- 報酬を得るためのリスクと、報酬を使う選択肢を設計する。成長が数字だけでなく挙動と外観にも反映されるようにする。
- 同じ背景色だけのステージ増殖を避け、**配置・高度・障害・射線・目標**を変える。
- 進行画面、イベント、ショップ、セーブは元ゲームを改修する場合は**原則維持**する。変える必要があるなら別の変更項目として宣言する。
- 実装件数・コード行数・自動テスト数を目的化しない。

## 4. 修正の進め方：原因→対策→回帰確認

1. **観測:** 何が違うかを対象画面・操作・端末・期待値で表す。スクリーンショットや短い動画が最優先の証拠。
2. **原因の切り分け:** 描画、入力遅延、物理、カメラ、UI、ルール、性能のどの問題か。**まずコードを調べて説明可能な仮説**を置く。
3. **変更範囲の限定:** 依頼箇所以外に触れない。関連変更が不可避なら理由と影響範囲を示す。既存ベースを保存し、別ブランチ／別ファイルで作業する。
4. **少数の大きな改善:** 重要な問題の解決を優先。見た目なら配色・造形・光、操作なら初動・追従・速度感など、原因に直結する部分から修正する。
5. **実画像・実入力で再確認:** 修正前後を同条件・同カメラ・同画面サイズで比較する。「コード上は直った」では終了しない。
6. **回帰確認:** 元の良い部分（操作、UI、マップ、装備、セーブ、ゲームテンポ）が変わっていないことを点検する。
7. **反復・収束:** 問題が残れば再修正。修正が新たな問題を生んだ場合は原因を分離して戻す。解決できないものは未対応として記載。

**修正報告フォーマット（AI）**

| 項目 | 記載例 |
| --- | --- |
| 問題 | 「旋回時、機体の側面が見えず平面的」 |
| 原因 | 「車体のヨー角が入力に対して最大6°程度しか変わらない」 |
| 変更 | 「旋回姿勢を大きくし、描画の側面とロールを追加」 |
| 変更しない | 「操作ボタン、マップ、既存の戦闘ルール」 |
| 確認 | 「左右切返し、停止、スマホ2指、前後スクショ」 |
| 未確認 | 「低スペック実機の発熱、30分以上の連続試遊」 |

## 5. QUALITY BAR：完成前の必須確認

**PATROL型の『完成と言う前に自分で撮って見て直す』を、今後のAI作業の標準手順として推奨する。** ただし確認内容は作品ジャンルと依頼範囲に合わせる。

| Gate | 必須の確認 | 失敗した場合 |
| --- | --- | --- |
| Q1 静的 | HTML/JS構文、アセット参照、ゲーム開始処理、必要な分割ソースとの一致 | 起動できるまで修正 |
| Q2 画面 | 初回画面、通常プレイ、最も派手な場面、結果／メニュー。**実ブラウザ撮影** | 主役の形・密度・配色・見切れを見て修正 |
| Q3 操作 | キー・マウス・タッチの主操作、同時押し、離した時、逆入力、連打 | 実際の入力イベントで修正。数値の診断だけで代替しない |
| Q4 ループ | 勝利／敗北、再試行、ステージ進行、強化、セーブなど実装した全主要分岐 | 到達できるまで修正 |
| Q5 端末 | PC・スマホ縦・スマホ横。ボタン重なり、画面外、誤タップ | 各サイズの画像を比較し修正 |
| Q6 負荷 | 多数のエフェクト、連続操作、低FPS想定、ランダム入力、コンソールエラー | FPS対策、リソース解放、例外対処 |
| Q7 回帰 | 改修前に守ると宣言した機能とUIが変わっていない | リグレッションを修正／変更を取り消す |
| Q8 試遊 | 自然な操作で遊べるか、楽しさの核が伝わるか、実機の体感はどうか | 自動テストの合格だけでは人間評価を済ませたと扱わない |

**画面撮影の最低セット:** 新作なら「タイトル／開始」「主操作中」「一番の見せ場」「結果」の4枚を基本とする。視点が3種類なら3視点すべて、飛行／射撃なら着弾、分岐ゲームなら地図、パズルなら成功前後を追加する。作品の特徴を判定できない画像を撮って合格とはしない。

**自動試験の最低セット:** ブラウザのJS例外を捕捉。PC／スマホ縦横で主入力を実行し、できれば一定時間のランダム入力で壊れないか確認。端末性能・発熱を実測していないのに「スマホ60fps保証」と言わない。シミュレーション時間と実時間、software WebGLと実GPUを区別する。

**合格の定義:** ①仕様に対応する動作、②実画面の見栄え、③入力、④ループ、⑤既存機能の保持、⑥未確認事項の開示。必須ゲートが未合格なら**試作／未検証**として渡す。ユーザーが公開判断するまで、技術テストの緑だけで正式公開しない。

## 6. GitHub・版・公開の運用

- **編集元・試遊HTML・公開ページを区別する。** GitHub Pagesへの反映、PR作成、mainへのマージ、X投稿は別の作業とし、実施できた範囲を明示する。
- 既存作品の改修は対象版と最新ブランチを確認。開発ブランチ／ドラフトPRで保存し、現行公開版を壊さない。既存の保存キーを無断変更しない。
- 新しい作品の仕様は `specs/<game-id>.md`、遊べる版は `games/<game-id>/index.html`、画像比較は `evaluation/<game-id>/` などに整理する（実体に合わせて調整可）。
- スクリーンショットは**実際のその版の画面**だけを検証画像として渡す。イメージ画像と実画面を混同しない。
- 公開承認・マージ・X投稿の範囲は最新の明示依頼に従う。開発停止や公開済み凍結は尊重する。
- 4部門（統括・制作・評価・動画）の役割を用いる場合は、成果物と責任を分離する。別々の常駐AIが稼働していると表現しない。

## 7. 過去事例から得た教訓（出典を区別）

| 作品／事例 | 確認できる事実（U／I） | 本書での運用上の教訓（P） |
| --- | --- | --- |
| 二重振り子ブランコ | 本人は位相、軌跡、靴追従、漕ぐ／射出だけの主操作を重視 | 物理の楽しさと入力の意味を最優先。表示やボタンを増やしすぎない |
| 投石機研究所 | カウンターウェイト、橋3本の破壊、横スクロール、動く標的、ボタン重複解消を要求。開発終了 | 主機構・標的の視認性・地形と当たり判定の一致を先に検証。凍結版は触らない |
| ロボサルベージ2D | 武器・脚部・装甲・コア、分岐マップ、ドット絵UIと装備変更が核 | 成熟作品の派生でゲーム進行やUIを勝手に置き換えない |
| ロボTPS試作 | 本人が速度感、機体デザイン、UIとマップの変更に不満を示し、開発中止を指定 | 技術的な3D化が成功しても元の魅力が失われれば失敗。仕様と評価を分ける |
| 10秒分身ダンジョン | 分身戦闘、罠誘導を希望。ゲーム画面から文字を撤去する指示が共通化された | 操作の学習を説明文ではなくゲーム内の現象で伝える |
| Pixel-art Splat試作 | 粒子破壊アクションと視点で橋を作るパズルを比較試作 | 特殊描画が実際の操作・勝敗に意味を持つ設計を優先 |
