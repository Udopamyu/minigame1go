# ミニゲーム1GO 開発方針・共通指示書

更新：2026-11-17（日本時間）。対象：新作と既存作品の開発・改修・評価・公開準備。

目的は、二重振り子ブランコ靴飛ばし、投石機研究所、ロボサルベージで繰り返した指示を引き継ぎ、同じ説明をユーザーに求めないこと。

## 最初に読むもの

1. [AGENTS.md](../AGENTS.md)：作業開始時の必須手順と現在の優先順位。
2. 本書：新作にも適用する共通方針。
3. 対象作品の仕様：[ブランコ](../specs/swing-shoe.md)／[投石機](../specs/catapult.md)／[ロボサルベージ](../specs/robo-salvage.md)。
4. 不一致があるときは[決定履歴](game-decisions.md)と、対象リポジトリの最新ソース・PRを確認する。

## 指示の扱い

- 最新のユーザー指示を最優先する。同じ作品・同じ項目について新しい合意があれば、古い指示を置き換える。
- **ユーザー指示（U）**、**実装確認（I）**、**今回整理した共通既定値（D）**を区別する。実装済みであることは、個々の値をユーザーが指定した証拠ではない。
- 共通既定値は過去3作品から抽出した開発の出発点。ジャンルや今回の明示指定に応じて調整する。
- 作品固有の回数・価格・全ロスト・1秒演出・ステージ数を新作へ一律に持ち込まない。新作の操作、長さ、成長方式は企画に合わせる。
- 原型、インクリメンタル版、2D本線、3D派生を区別する。別版の指示を上書きしない。
- 原発言を確認できない値は「実装値」または「未確認」と書く。古いコメント、計画、AIの提案を採用済み仕様に格上げしない。

## 最重要：ゲーム画面に文字を入れない（U・2026-11-17）

ユーザーの明示指示：「人間は画面に文字があると疲れちゃうから、極力文字は入れない」「ゲーム画面に文字は入れない」。今回だけでなく、今後のゲーム制作へ引き継ぐ。

- 通常のプレイ画面では、タイトル、ブランド名、バージョン、キャッチコピー、見出し、説明文、常設の操作案内、凡例、ボタンの文字、状態ラベルを表示しない。短い文や英語に置き換えて残すこともしない。
- 操作はアイコン、状況は絵・動き・形・ゲージ・効果音で伝える。扉とスイッチなどの対応は形と色を併用し、色だけに依存しない。
- 時間・HP・分身数なども、まずゲージ、図形、個数で表現する。数字を無条件に常設しない。
- 詳細や操作説明が必要な場合は、ユーザーが自分で開く別のヘルプ・設定・詳細画面へまとめる。画面に見えない読み上げ用ラベルは維持する。
- 説明がないと分からない遊びは、ステージ配置、短い実演、操作への反応で覚えられるようにする。文字を減らした結果、判別不能なアイコンだけが並ぶ画面にしない。
- 従来の「説明を短く」「短い情景文」「ボタン名で伝える」より、この最新指示を優先する。既存作品を改修するときにも適用するが、開発終了した作品を依頼なしに再開しない。

## 共通の開発方針

| 項目 | 現在の共通方針（Uの明示指示をDの既定値より優先） | 元になった指示 |
| --- | --- | --- |
| 遊びの核 | まず核の操作が気持ちよく成立する、遊べる版を作る。物理・戦術・強化は実際の挙動に反映する | ブランコの漕ぎ／射出、投石機の動く重り、ロボの装備効果 |
| 操作 | 主操作を絞り、必要な場面で必要なボタンだけを表示する。調整・情報はメニューへまとめる | ブランコの漕ぐ／射出、投石機の改造ボタン、ロボの左上メニュー |
| 文章 | **通常のゲーム画面に文字を入れない（U）**。タイトル・説明・見出し・ボタン文字・状態ラベルを撤去し、絵・動き・アイコンで伝える | 2026-11-17の明示指示。従来の短文化方針を置き換える |
| 情報 | プレイ中はゲージ・形・個数で伝える。強化の詳細数値や交換差は必要時に開く別画面で示し、計算との一致を保つ | ロボの数値の正確さを維持しつつ、2026-11-17の文字撤去指示を優先 |
| 見た目 | 指定がなければドット絵を有力な出発点にする。機体・背景・UIを揃え、輪郭と形を描き分ける | 投石機のドット調、ロボの本格ドット絵指定 |
| 変化 | 装備・敵・地形の違いを、形・動き・攻略法で分かるようにする | ロボの4部位の外見、投石機の橋／城／移動戦車 |
| 物理 | 動く機構、地形、見えている物体と当たり判定を一致させる。タイミング操作に意味を持たせる | 二重振り子の位相、投石機の重りと射出、橋・高台 |
| 成長 | 強化によって遊び方と手応えが変わるようにする。物理調整系では、購入した能力の範囲内で下げる設定も検討する | ブランコ長の再調整、投石機の有効強化Lv、ロボのビルド |
| ステージ | 配置の反復を避け、背景・地形・敵の動き・ギミックを変える。背景だけでなく攻略にも変化を出す | 投石機後半、ロボの戦場形状・分岐 |
| 演出・音 | 射出、速度、命中、破壊、勝敗などに効果音と視覚的反応を付ける。戦闘前後には短い区切りを作る | ブランコ4効果音、ロボのBGM・破壊演出 |
| カメラ | 標的、機体、飛翔物、結果を見失わせない。必要に応じてスクロール・追従・ズームを使う | 靴追従、投石機の標的可視化、ロボの勝敗ズーム |
| 端末 | PCとスマホの両方で遊べる設計にする。縦横でボタン重複・画面切れ・文字の小ささを確認する | 既存3作品の対応、改造／炸裂弾ボタンの重なり修正 |
| 試遊 | 操作・戦術・再挑戦を実際に試す。自動操縦の敗北だけを理由に簡単にしない | ロボについての「意外とクリアできる」という本人の評価 |

ドット絵、ローグライト、全ロスト、BGM、全画面化などは、ジャンルを無視して強制する条件ではない。3D TPSなどの明示指定はそのまま尊重する。

## 作業の進め方

1. 対象作品と現状を特定する。完成済み作品、試作、公開済み版、別路線の派生を取り違えない。
2. 共通方針と作品仕様を読んでから実装する。既に決まった事柄を再質問しない。
3. 未指定の細部は、面白さ・操作性・整合性を基準に判断して進め、重要な判断を記録する。
4. 新作は[企画テンプレート](../specs/new-game-template.md)で核・操作・成功条件を短く定義する。不要な欄は削る。
5. 実装→試遊→修正を回し、遊べる成果物を出す。行数、画面数、テスト数だけで完成と判断しない。
6. ユーザーの修正を受けたら、該当仕様の現在値を更新し、置き換えた内容を決定履歴へ残す。変更のない項目は維持する。
7. 最後に、変更点、確認したこと、残る問題、遊べるファイルまたは実在するURLを簡潔に伝える。

「残りは面白くなるよう判断して実装」の裁量は、合意済みの核・終了方針・公開範囲の変更を意味しない。新しい重大な分岐だけを確認し、通常の実装判断で止めない。

## 追加描画オプション：軽量ピクセル擬似3D（2026-11-17）

- 共有されたXの3件から、Sprite Stacking（層を回転して疑似立体化）、Pixel-art Splat風の粒状表現、低解像度Canvasでの飛行・地形表示を研究。
- 具体的な描画アルゴリズム・適用作品の判断・性能評価上の注意点は [軽量ピクセル擬似3D技術ノート](lightweight-pixel-pseudo3d.md) に記載。
- 導入はユーザーが対象作品を指定した時、あるいは作品固有のゲーム性に明確な利点がある時に提案する。学習しただけで全作品の既存表示を変えない。作者が非公開の方式を使ったと断言しない。

## 技術・保存・評価の既定値

- 無料・広告なしのブラウザゲームを基本とする。過去の運用はHTML/CSS/JavaScript。新作の構成は目的に合わせる。
- 配布物と編集元を区別する。単体HTML配布が合意されている作品では、分割ソースから再生成して一致を確認する。
- 進行・強化・自己ベストを保存する作品では、既存の保存キーと移行条件を確認する。更新で意図せずデータを消さない。
- デバッグ用のHP・所持金変更や調整UIを、通常プレイ・難易度評価・投稿動画と混同しない。
- 変更に応じて、起動、主要入力、購入／交換、勝敗、再挑戦、保存、PC／スマホ表示を確認する。
- 「静的検査」「機能テスト」「通常入力での試遊」「人間のゲーム性評価」「公開URL確認」を別々に記録する。
- 一部の到達・動作が確認できただけで、全ステージ攻略・全端末動作を合格扱いにしない。未確認はそのまま記録する。
- AI操縦の成績と人間の難易度を分ける。詰まり、射線、被弾、回復、経済、操作性の具体的な問題から調整する。

## 公開・動画・投稿

- 依頼で指定された範囲まで進める。公開承認済みの同じ版について、古い「承認待ち」を理由に再承認を要求しない。
- ゲームの公開とX投稿を分ける。Xには自動投稿せず、投稿文を準備する。投稿そのものは新しい明示依頼が必要。
- 動画は検証済みのゲームの実プレイ。通常の運用目安は縦10〜20秒。ロボv0.15の公開依頼は**5〜10秒程度**であり、個別指定が優先。
- 機能テストの途中を録っただけで紹介映像完成としない。見せ場、尺、表示、再生を確認する。
- `videos/<ID>/` に実動画・台本・投稿案・検証記録を対応付ける。存在しない動画や未確認の公開URLを完成品として渡さない。
- X運用の既定は動画中心の本文とゲームリンク用の返信案。投稿形式を指定された場合はその指示を優先する。
- 4部門の責任分担は[ワークフロー](four-team-workflow.md)を参照する。別々の常駐AIが実在するとは表現しない。
