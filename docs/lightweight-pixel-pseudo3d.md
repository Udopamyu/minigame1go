## 1. Sprite Stacking：既存2D描画へ段階的に追加可能

- 1枚のシートに、オブジェクトの高さごとの水平スライスを並べる。下層から順に描き、スライス番号 z の分だけ画面上で上にずらす。
- オブジェクトの進行方向（または独立した向き）で**すべての層を同じ角度に回転**し、必要に応じて縦方向を0.75前後へ圧縮。Nearest Neighborで原色・輪郭を保持する。
- 原点を接地点とし、オブジェクト全体を接地点Yで奥行きソート。1層ごとに別オブジェクトとソートしない。
- 原典の参考例：15層、各24×43 px、層間1内部ピクセル、squash=0.75。これらは例示値でありゲーム共通固定値ではない。
- 元素材：MagicaVoxelでボクセル層を描く、または上・横・正面・背面の4面図から層を生成。無料のブラウザ変換ツール https://www.spritecook.ai/sprite-stack-generator もある。
- 注意：スライスへの輪郭の二重描画、回転時ジャギー、薄い部品・空洞、何百個もの再描画による性能低下。静的なものは回転後の画像を事前キャッシュする。

アルゴリズム例（説明用の疑似コード、ゲームエンジン依存）：

```js
for (let z = 0; z < slices.length; z++) {
  // スライスを中心で angle 回転、必要なら縦を squash 倍
  // x は接地点、y は接地点 - Math.round(z * spacing)
  drawRotatedNearest(slices[z], x, y - Math.round(z * spacing), angle, squash);
}
```

## 2. Pixel-art Splat風表現：視覚効果と実装方式を分離

- 目標は、ピクセル単位でちらつく粒子や立体感のある点描・奥行き表現。雰囲気の再現が目的なら、巨大な3D Gaussian Splattingシーンを実行することが必須ではない。
- **独自の実装案（原投稿が採用した方法ではない）**：少数のワールド座標つき色粒子・billboardを画面に射影し、画面距離と深度で大きさを調整。最終出力は固定パレット・低解像度バッファへ量子化し、最近傍拡大する。必要なら簡単な深度マスクで手前を隠す。
- 当たり判定は粒子ではなく、2Dのコリジョン形状・地形マスク・高さマップなど別の単純な論理表現を使用する。
- 性能ベンチとモバイル動作を確認してから導入。**原投稿から速度や軽量化率は引用しない。**

## 3. 2D Canvasだけで作る擬似3D飛行表示

- 描画：内部フレームバッファ（例：300×250）へピクセル単位で描き、CSSの `image-rendering: pixelated` とnearest拡大で表示。
- 飛行機：数十枚の2Dスライスを回転・積層。島・海：2Dのノイズから高さマップを作り、地表を低解像度で投影。雲も別の高さ層に置く。
- カメラ：俯瞰視点から追跡視点へ、傾き・距離・高さ・向きを補間。新旧のシーンを切替えず連続遷移にする。
- 深度処理：距離による縮小、遠方の彩度低下、占有マスク（簡易な前後処理）などを使う。衝突判定は独立した2Dマップで行い、描画ピクセルそのものを物理判定にしない。
- 上記は作者の「no 3D engine / no polygons」の説明と第三者の技術分析に基づく**実装方向の要約**であり、元作品の内部コード再現を確認したものではない。

## ミニゲーム1GOへの適用判断

| 作品・将来案 | 推奨 | 理由 |
| --- | --- | --- |
| 10秒分身ダンジョン | 現時点では見送り。採用するなら高低差・回転するトラップ等に限定 | 時間分身・視線・予告・罠の判別を優先し、重ね絵で視認性を損なわない |
| ロボサルベージ 2D | 機体・回転砲・旋回する敵、残骸への局所的な試験 | パーツ形状を維持しながら向きを滑らかに変える余地がある |
| 新作の飛行／レース／俯瞰アクション | 有力な採用候補 | カメラ変化と連続回転がゲーム性へ直結 |
| 背景・演出 | Pixel-art Splat風の軽量描画を局所利用 | 物理判定や主要敵の視認性から切り離して試験できる |

ゲーム共通指示「**プレイ画面に文字を入れない**」を維持。新しい描画技術を導入する場合も説明文字で補わず、ゲーム内の動き・カメラ・アイコンで伝える。

## 導入時の最低限の評価

1. 2D基準版と新表現版を切り替えて、**当たり判定・向き・射線・奥行き整合**が崩れないか。
2. PC/スマホの実ブラウザで、FPS・CPU使用率・入力遅延・画面切れを比較（ベンチ結果がなければ性能優位と主張しない）。
3. 低解像度の見せ方を守り、nearest拡大時のちらつき・輪郭・可読性をチェック。
4. 既存ゲームへの適用はユーザーのゲーム修正依頼があったときに実施し、**学習と実装済みは区別**。
