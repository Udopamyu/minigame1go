## 原則の概観（資料の要約）

### 1. 目的とゲーム性
- 最後の判断軸は「遊ぶ人を楽しませること」。作り手の苦労や好みは遊ぶ人に伝わらない。
- 駆け引きはリスクとリターンの配置で生まれる。危険を負う行為に見合う利得を置き、プレイヤーが危険を減らす攻略を考えられるようにする。
- 緊張や障害を与え、成功・撃破・成長などで解消する流れを考える。ただし、駆け引き以外の面白さ（操作感、物語、再現性など）もある。
- キャラクターや敵の長所短所を平均化しすぎない。尖った特徴が選択と攻略を生む。
- 参考：`references/gameplay.md` の動画 **006、009、026、216**。

### 2. 難易度・再挑戦・報酬
- 開発者は操作に慣れているため、初見の難易度を過大評価しやすい。救済や難易度変更を検討し、クリア不能の行き詰まりを避ける。
- 失敗から再操作までを短くする。再挑戦の気力を失わせない。
- ご褒美は制作後の付け足しにせず、先の目標や選択肢と結びつける。強くなる実感と、得た資源の使い道が重要。
- 難所を一直線に並べず、挑戦と緩和の起伏を設計する。
- 参考：`references/gameplay.md` **075、105、116、127、211**、`references/planning.md` **023**。

### 3. 企画・導入・テンポ
- 別作品の表面的な模倣ではなく、面白さを分解・考察して新しい仕組みに再構築する。
- 序盤は説明や長い演出より、ゲーム自体の楽しさを触って理解させる。チュートリアルは本編の文脈に組み込む。
- 何もできない時間、画面遷移、スキップできない演出を減らす。ボタンの無反応も避ける。
- 参考：`references/planning.md` **017、057、085、104**、`references/specs.md` **073、244**。

### 4. 操作感・カメラ・物理仕様
- 速度、慣性、加減速、ジャンプ、フレームレートは、操作時の「軽い・重い」の印象を決める。速度の単位を定義して調整する。
- 画面上の動きは操作入力への即応が重要。アナログスティックは倒す量だけでなく倒す速さも入力にできる。
- 3Dカメラは常にキャラクターに固定追従させるとは限らない。特に縦の追従を弱めると高さやジャンプを理解しやすくなる。
- ジャンプは初速と重力の設計から始め、空中制御・上昇と下降の速さを作品目的に応じて調整する。
- 参考：`references/specs.md` **019、037、061、084、152**。

### 5. 攻撃・モーション・ヒット時の手応え
- 待機 → 構え → 攻撃 → フォロースルーを意識し、入力の最初のフレームで反応を見せる。
- ヒットの瞬間のポーズ・停止・反動・効果音・エフェクトを組み合わせて結果を認識させる。
- 大げさな動きは小さい画面ほど必要になることがある。一方、見た目の揺れと当たり判定は分離して考える。
- 参考：`references/motion.md` **028、036、049、062**、`references/specs.md` **003、047**。

### 6. 視覚エフェクト
- 単なる発光・加算合成だけで済ませず、輪郭と明暗のはっきりした形を使う。
- 爆発・振動・ヒットマークには時間的なメリハリを付ける。効果を派手にしてもキャラクターや判断に必要な情報は埋めない。
- パーティクルは量を増やすだけではなく、寿命と画面上の情報量を調整する。
- 参考：`references/effects.md` **016、035、056、103、130、242**。

### 7. グラフィック・アートディレクション
- 単なる物体色ではなく、光の当たり方・色相の変化・遠近の空気感を描く。
- 判定のある床や障害物は視認しやすく、背景は主役を邪魔しないように整理する。
- シルエット、描き込み密度、質感、彩度などを作品内で統一する。スケール感は形だけでなく素材や画角でも変わる。
- 修正指示は言葉だけより画像への直接レタッチが伝わりやすい。
- 参考：`references/graphics.md` **010、030、044、063、090、114、129、241**。

### 8. UI・アクセシビリティ
- 「分かりやすさ」と「スタイル」は両方を最大化できるとは限らず、ゲームの性格で優先順位を決める。
- 重要な操作や情報のサイズ、配置、色分けを工夫し、HUDは必要性に応じて表示する。
- 言語・画面サイズ・操作機器ごとに読みやすさを確認。入力変更、スキップ、ヘルプ、酔い対策などの選択肢も検討する。
- 参考：`references/ui.md` **018、033、055、145、178、195、238、252**。

### 9. サウンド
- 効果音の強さは、ゲーム結果への影響度や情報の重要度で優先づける。
- ヒット音は立ち上がりを明確にし、残響を過度に長くしない。BGMのテンポは操作の速さに合わせる。
- 実際のスピーカーやヘッドホンなど複数環境で確認し、音の演出を画面上の操作・結果と一致させる。
- 参考：`references/sound.md` **025、032、054、165**。

### 10. パラメーター調整・デバッグ
- 調整値をプログラム本体から分離し、変更を素早く実行結果に反映できるようにする。反復回数が調整精度に直結する。
- デバッグモードや確認ツールを用意して、特定の体力、カメラ、シーン、表示状態を再現・観察する。
- 仕事の受け渡しや不具合は担当・状態・再現手順の分かる形式で記録する。
- 参考：`references/tech.md` **046、094、193、215**。

### 11. チーム・制作判断
- 適切な場で決断し、修正案を伴うフィードバックを共有する。進捗が見える開発資料・スクリーンショットが役に立つ。
- 初見プレイヤーの言葉だけでなく、詰まる・迷う・飽きる瞬間の実際の反応を観察する。
- 制約が厳しいときは、全てを残すより、面白さの核を優先して要素を削る判断も必要。
- 参考：`references/team.md` **043、060、189、246、256**、`references/mindset.md` **185**。

### 12. コンセプト・企画の伝え方・広報
- 企画の柱を一言で説明できるようにし、作品ごとの課題と独自の解決策に落とす。
- 企画書やプレゼンは図と簡潔な文を軸に、伝える内容を絞る。
- 宣伝で見せる作品像は実際の内容と一致させ、ゲームプレイの魅力を早い段階で見せる。
- 参考：`references/concepts.md` **004、011、059、124**、`references/mindset.md` **038、185**、`references/pr.md` **080、101、184**。
